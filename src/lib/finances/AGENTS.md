- FIN-04 : recherche Finances = contrat unique (lib/finances/query.ts → fin_select / fin_pay_select) pour écran, totaux et CSV; vues dans fin_saved_views (RLS fin_can_*) — aucune divergence entre écran et export.
- FIN-05 : trésorerie calculée côté client par un moteur pur (src/lib/finances/treasury.ts) sur les données lues sous RLS; scénarios = copies en mémoire, jamais d'écriture sur obligations/règlements — une seule logique testable.
- FIN-06 : rappels générés et distribués côté serveur par fin_reminders_sweep (dans la tâche existante crm-notifications-sweep, 10 min); dédup par dedupe_key + unique(rappel, destinataire, canal); courriel/texto en mode test (« simulé », aucun appel externe) — pas de dépendance à l'ouverture d'une page.
- FIN-06B : la cloche entrepreneur lit les rappels « application » via fin_my_bell (même source fin_reminder_deliveries, droits revérifiés à chaque lecture) — aucune deuxième file; adresse absente = échec permanent sans reprise.
- FIN-07 : taxes = un seul moteur (public.fin_tax_compute, miroir exact src/lib/finances/tax.ts), taux versionnés dans fin_tax_rates; entcrm_quote_freeze recalcule côté serveur et fige tax_snapshot à la remise (bloquée si non résolu); taxes incluses : chaque taxe = total × taux / (1 + taux cumulés), base = solde; documents sans instantané jamais recalculés — jamais de taux copiés dans un écran ni de totaux du navigateur.
- FIN-08 : factures = brouillon recalculé par trigger, émission par fin_invoice_issue seule (numéro sous verrou fin_invoice_settings FOR UPDATE + index unique, contenu figé en snapshots, une entrée attendue liée); PDF rendu par invoicePdf.ts depuis les snapshots et stocké dans le bucket privé fin-invoices (dossier = entreprise, aucun écrasement).
- FIN-08B : encaissements clients = fin_invoice_receipts (jamais fin_payments fournisseurs), écrits seulement par fin_invoice_receipt_add/void (clé d'idempotence, annulation motivée); l'entrée attendue liée reçoit received = min(montant, legacy_received + encaissements actifs), modification directe bloquée; trop-perçu calculé, jamais réaffecté.
- FIN-09A : notes de crédit = fin_credit_notes, écrites seulement par fin_credit_save(…, _base_rev)/discard/issue(…, _expect_rev, _expect_hash)/set_pdf (aucun INSERT/UPDATE/DELETE direct); fin_credit_compute interne (aucun EXECUTE client), depuis tax_snapshot de la facture (jamais le profil actuel), indices stricts, arrondi cumulatif par ligne et taxes cumulées, jamais de troncature (refus explicite, mode « balance » = résidu exact); émission vérifiée par révision + empreinte (écart = P0409, pas de réémission auto); verrou facture puis avoir puis réglages; solde unique fin_invoice_balance (brut − avoirs émis − encaissements, plancher 0) utilisé par sync/summary et la fiche; facture entièrement créditée = entrée attendue archivée.
- FIN-09B1 : facturation progressive = fin_progress_plans (un par soumission, contrat figé) + fin_progress_situations (un brouillon actif), écrits seulement par fin_progress_plan_create/draft_save/issue/abandon; fin_progress_compute(…, _on) interne : plafond cumulé HT (contrat HT) ou TTC (contrat taxes incluses, mode amount_ttc; amount HT refusé), parts du plafond par traitement après − avant; taxes de CHAQUE facture par fin_tax_compute sur sa part (jamais ajustées vers la taxe arrondie de la soumission); écart vs soumission exposé dans gap_vs_quote; factures progressives liées par progress_situation_id (jamais quote_id), exclusivité par FAMILLE de révisions (fin_quote_family_root/fin_quote_family, verrou fin_inv_qfam:racine) pour fin_invoice_from_quote et les dossiers, parent non modifiable si famille engagée; rejeu émission/abandon = clé + révision + empreinte identiques sinon P0409; avoirs ne rouvrent pas le plafond; taux/profil différent du contrat = refus.
- FIN-09B2 : suivi du dossier (fin_progress_plans.track global|lines|milestones) choisi avant toute émission puis verrouillé; contrat en vigueur = plans.lines/contract + contract_version, versions immuables dans fin_progress_contract_versions; lignes : part = montant cumulé arrondi par ligne − déjà facturé (computed.line_parts); jalons fin_progress_milestones (réalisation ≠ facture, facturé immuable); avenants fin_progress_amendments (seul l'approuvé crée une version; jamais sous le déjà facturé); tout passe par fin_progress_compute_any interne et les RPC fin_progress_* (verrou dossier d'abord) — une seule source de plafond, aucune écriture client directe.
- FIN-09C1 : factures récurrentes = fin_recurring_templates/versions/occurrences/events, écrits seulement par fin_rec_* (verrou modèle → occurrence → facture → numérotation); dates par fin_gen_dates seul; préparation explicite (≤ 24) en brouillons sans numéro ni entrée; émission fin_rec_issue = une facture liée (recurrence_occurrence_id protégé) + une entrée attendue; versions seulement après la dernière occurrence réservée; abandon = occurrence conservée, jamais recréée; aucun cron, aucune émission ni envoi automatique.
